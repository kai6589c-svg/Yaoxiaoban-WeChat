# 药小伴：GitHub 参考项目融入计划

- 日期：2026-09-16
- 状态：P0 / P1 已进入 beta.19 实现；代码验证和发布门槛见[交付记录](../beta19-reference-integration.md)，真机验收仍待完成。
- 代码基线：公开仓库 `kai6589c-svg/Yaoxiaoban`，`main`，提交 `8206647`，版本 `0.5.0-beta.18`。
- 工作目录：公开仓库工作副本 `yaoxiaoban-github`。原生产工程及其历史继续保留，不把内部历史合入公开仓库。

## 1. 目标与范围

围绕三个用户问题改进现有产品：保存好了没有、计划设置对不对、家里的药在哪一盒。优先复用现有领域规则、数据服务和云函数，不重写架构。

第一轮聚焦照片恢复、计划预览、今天与历史状态、通用交互。第二轮增加位置、新购一盒和引导盘点。单药盒暂停提醒在语义及通知渠道边界明确后单独实施。

本计划不包含 OCR、AI 用药建议、自动推荐剂量、药品商城、多人账号实时协作、全量组件库替换或改用其他云平台。多盒展示不引入跨盒自动扣减库存。

## 4. 第一轮：保存、计划与记录更清楚

### P0-A 照片恢复与状态呈现

**目标**：照片失败后可以继续处理，用户不需要重复填写药盒，也不会因为错误提示新增重复药盒。

拟修改：

- `miniprogram/services/save-queue.ts`
- `miniprogram/services/medication-photo.ts`
- `miniprogram/services/data-service.ts`
- `miniprogram/pages/sync/index.*`
- `miniprogram/pages/medicine-form/index.*`
- `miniprogram/pages/medicine-detail/index.*`
- `miniprogram/pages/cabinet/index.*`
- 新增 `miniprogram/services/save-job-view.ts`，把任务事实转换为统一文案和可操作项。

设计：

1. 保留现有执行状态，不仅靠 message 字符串判断动作。补充可选的失败代码、失败阶段、字段确认状态、照片确认状态与本机文件可用性。旧任务加载时保守归一化，不能因为 draft.id 存在就判定本次编辑字段已保存。
2. 显示“药盒信息待确认”“药盒信息已保存，照片待同步”“照片结果待确认”“照片已保存”等不同状态。缩略图后台处理不阻挡已确认主图的成功反馈。
3. 新增明确的“重新选择照片”动作：先核对云端状态；若原图已绑定，不再重复上传；若确认未绑定且本机文件丢失，只补照片，不重新提交字段和初始盘点。
4. 拟增加队列的照片修复入口，复用已有 `getMedicationPhotoStatus`、`prepareMedicationPhoto` 及完成上传流程。只有确认药盒存在且获取最新版本后，才创建新的照片任务。具体方法名实施时确定。
5. 同一张照片的重试复用其稳定请求 ID；选择了不同照片必须使用新任务/新票据，不能用旧幂等 ID 携带不同内容。旧任务要先完成结果核对和失效处理，防止迟到结果覆盖新照片。
6. 药箱和详情从同一状态转换函数获取提示，不新增逐卡网络请求或高频轮询。账号切换后不得显示上一个账号的本机任务。
7. 继续保留最大任务数、恢复期限和重试上限。首次字段保存结果不确定时，不允许通过重选流程绕过防重复机制。

验收：普通成功、离线、响应丢失、退出重进、本机文件丢失、票据过期、跨设备修改、账号切换均有明确结果。重选照片不新增药盒、不重建计划、不重复记录初始库存；结果未确认时不显示成功。

测试入口：扩展 `tests/save-queue.test.ts`、`tests/photo-selection.test.ts`、`tests/medicine-form.test.ts` 与云端 `photo-fast-path.test.js`、`photo-store.test.js`；新增任务状态映射测试。UI 测试覆盖同步页的恢复动作。

### P0-B 未来 7 天计划预览

**目标**：用户在保存前就能确认时间安排，不必通过保存后反复编辑来核对。

拟新增 `miniprogram/core/plan-preview.ts`；修改 `pages/medicine-form/index.*`，复用 `core/schedule.ts`、`core/dates.ts`、`core/expiry.ts`、`core/validation.ts`。

设计：

- 将表单草稿转换为仅用于计算的临时计划，调用现有 `expandOccurrences()`；不落库、不申请提醒权限、不新增网络请求。
- 范围明确为“今天起 7 个上海自然日”，只展示当前时刻之后的安排；单日显示时间和用户填写的数量。
- 新增与编辑均使用与正式保存一致的生效规则，排除被替换的旧计划。临时 ID 不得成为真实 occurrenceKey。
- 受计划结束日期和药盒有效管理日期共同限制；按需模式显示“按需记录，不生成固定安排”。
- 表单未填完整时提示缺少什么；近期没有安排时说明下一次超出预览范围，不误报为计划无效。
- 表单变化后本地重算，合并频繁输入更新；不在每个键入动作触发云请求。

验收：每日/指定星期、跨周/月/年、月精度效期、开封期限、当天时刻已过、计划未来开始、编辑生效时间、没有安排均正确。固定测试时钟后，预览结果与保存后同一窗口的计划展开一致。

测试：新增 `tests/plan-preview.test.ts`，扩展 `tests/schedule.test.ts` 和表单集成测试。预览不改变现有计划、库存和服药记录。

### P0-C 今天与历史状态整理

拟修改 `pages/today/index.*`、`pages/history/index.*`；需要时新增 `core/task-presentation.ts`。复用 `services/intake-queue.ts` 与现有撤销接口。

设计：

- 今天页保留重点任务卡，将列表清楚区分为待处理、接下来、已记录；`needs-review` 独立显示核对入口。
- `due` 的产品文案为“到时尚未记录”，不自动推断漏服。只有用户明确选择 skipped 才显示已记未服。
- 排序固定，同时间任务按稳定标识排序；刚点击的任务不因列表跳动导致用户点错下一项。
- 本机记录已落队列但云端未确认时显示“记录待同步”，保留原始 occurredAt。撤销与待同步冲突时，先按现有队列规则核对，不新增无法追踪的乐观撤销。
- 历史页同时展示“计划时间”和“记录时间”；额外使用没有 scheduledAt 时只显示实际记录时间。撤销后的记录不重新计入有效记录。
- 本轮不新增服药评分、连续天数奖励或按时率指标，也不修改库存算法。

验收：未记录/未服/已服不混淆；一条待同步记录不会与云端确认记录重复显示；重复点击、重试、撤销和跨天展示正确。

测试：扩展 `tests/dashboard.test.ts`、`tests/intake-queue.test.ts`，新增今天和历史的呈现测试。若改变共享 Today DTO，必须修改 TS 源码并通过 `scripts/build-shared-domain.mjs` 重建，不能手改生成的 `dashboard-shared.js`。

### P0-D 通用交互与无障碍

贯穿以上三项，不作为最后才处理的美化工作。

- 基于 `miniprogram/app.wxss`、`components/app-nav` 和现有页面样式，统一主次按钮、禁用/忙碌状态、错误区、空状态和字号缩放。
- 提取拟议的 `components/status-notice`，仅在多个页面需要相同“状态＋说明＋动作”结构时使用，避免为单一页面增加抽象。
- 错误定位到具体字段；图片上传失败不清空表单；图标按钮的可访问名称包含动作与对象。
- 统一重要触控区域，设计目标至少 44×44 逻辑像素，并在实际设备上检查字号放大、底部安全区和读屏焦点。
- 小规模比较 TDesign 按需组件与现有组件，记录包体差异；第一轮默认不新增 UI 库依赖。

## 5. 第二轮：更贴近真实家庭药箱

### P1-A 存放位置

增加可选 `storageLocation`，第一版使用短文本及本账号已有值建议，不新增位置集合和位置 ID。

代码路径：`core/models.ts` 的 Medication/MedicationDraft、`core/validation.ts`、`services/data-service.ts` 的本机与云端路径、`medicine-form`、`medicine-detail`、`cabinet`、`services/readable-export.ts`。

后端路径：`compat-schemas.js` 白名单与长度校验、`compat-service.js` 写入及 `toMedication` 映射；检查旧 `schemas.js` / `service.js` 路径对新字段的保留行为。同步更新数据模型文档。

兼容规则：旧数据缺失视为未填写；新客户端可明确传空值清除；旧客户端未提供字段时保留原值。建议上限 30 个字符，不将位置写入诊断日志。先在现有账号药箱数据中筛选，不因这一字段新增数据库索引或全库迁移。

验收：本机模式、普通保存、快速照片保存、编辑、归档恢复、导出均保留位置；旧客户端编辑不抹掉新字段。

### P1-B 又买一盒与多盒展示

先实现快捷录入，再做可选展示分组，继续以独立 medicationId 为数据主键。

- 从详情页进入“又买一盒”，表单通过源药盒 ID 读取当前账号数据，不把药名等个人信息拼进 URL。
- 只预填成员、药名、规格、单位及可选位置。新盒有效期、数量必须重新确认；开封日期、照片、计划、历史、快照、业务版本和旧任务 ID 不复制。默认新盒为只记效期，用户主动选择后才设置计划。
- 首期可以不增加持久化关联字段。展示分组仅对成员、名称、规格、单位均明确且一致的药盒提供折叠；缺失或不确定时保持独立。
- 每盒显示位置、有效期、开封状态与余量；组内按管理日期稳定排序，但不以“先用”措辞推荐具体药盒。
- 不合并计划、不跨盒自动扣量，不因同名自动建立可互换关系。没有统一库存计算前不显示可能误导的跨盒预计总量。

代码路径：`pages/medicine-detail`、`pages/medicine-form`、`core/cabinet.ts`、`pages/cabinet`；新增 `core/medication-copy.ts` 保存明确的可复制字段清单。

验收：新建成功后源盒完全不变；同名不同规格或不同成员不混合；两盒有不同有效期、盘点和计划时相互独立；照片队列重试不造成重复新盒。

### P1-C 引导式集中盘点

新增 `pages/inventory-session/index.*` 与 `services/inventory-session.ts`，在 `app.json` 注册入口；继续复用单盒盘点的 `DataService.confirmInventory()` 及验证。该接口已有可选 `recordedAt` 和 `requestId`，会话需要固定并持久化这两个值；当前单盒页面每次点击才创建请求 ID 的方式不能直接用于中断重试。

- 用户按成员或位置选择药盒，逐盒录入实际余量，支持跳过和稍后继续。
- 会话只保存账号范围、药盒 ID、进度和当前输入；不另建一套云端库存。每盒成功提交即成为正式盘点快照。
- 显示“已完成 3/8”，仅服务端确认成功后标记完成。第一版离线只保留草稿，不承诺盘点自动云同步。
- 单盒提交使用稳定请求 ID；响应未知时核对原请求结果，不用新 ID重复产生快照。实施前确认现有快照接口对该场景的幂等能力，不足则先补接口。
- 实际盘点时间在用户确认时固定；跨天重试不能改成重试时刻。每盒独立提交，不执行长事务；归档、删除或版本冲突的药盒停下核对。
- 切换账号隔离会话；已完成快照不可由“取消本次盘点”回滚，取消只清除未提交草稿。

测试：会话恢复、重复请求、未知响应、跨天、账号切换、部分失败、药盒被归档、数量为零和单位校验。库存计算继续以已确认的快照为基线。

## 6. 后续独立项：单药盒暂停提醒

只在前两轮稳定且用户确认需求后进入实施。先冻结以下语义：暂停微信通知不改变计划、不改变预计消耗、不等于暂停用药或归档；恢复不补发暂停期间的提醒。

候选设计为药盒级可空 `reminderPausedUntil`（包含产品定义的长期暂停方式），但在确定“暂停一次、暂停到某天、长期暂停”需求后才冻结字段。

预计涉及 `core/models.ts`、独立提醒设置 RPC、提醒任务生成、`reminder-worker/lib/worker.js` 发送前回查、`reminder-health.ts` 和详情组件。使用窄范围设置接口，避免为关通知重新提交整个药盒草稿。

必须处理已领取任务和恢复操作的竞争、请求幂等、重复恢复及多设备修改。说明暂停生效前已发送消息无法收回；已导出的系统日历事件不能被这个开关静默保证停用，应独立显示处理提示。

验收要求：暂停状态影响未来通知资格，计划和库存结果不变；恢复只生成之后的合法安排，提醒摘要与后台决策一致。若无法清楚解释跨渠道效果，推迟该项。

## 8. 共同验收门槛

### 自动化

- 每个 PR 运行 `npm run check`，GitHub Actions 从全新环境安装并通过；新增测试数量由实际行为决定，不以凑数量为目标。
- 配置为正式环境后运行 `npm run release:check`；演示配置不能用于正式交付。
- 新字段验证本机/云端、普通/快速保存、旧/新客户端兼容；只改文案不重复编写业务测试。
- 复用 `tests/e2e/journeys.mjs` 扩展必要旅程。当前 Nightly 启动超时是已有验收阻塞；模拟器未就绪不能算 UI 通过，也不能用延长等待代替排查。

### 照片性能与恢复

- 保存点击到界面解除阻塞的验收上限保持 10 秒；保留 9,800ms 操作预算，不因添加预览或状态刷新增加串行 RPC。
- 普通网络下云端绑定确认 P95 目标不高于 8 秒；分别统计云端确认、页面解除等待、含跳转总时长，保留失败样本。
- iOS、Android 分别执行普通网络连续 30 次，弱网/离线/响应丢失等故障至少 10 次；记录机型、网络、图片大小和冷/热启动条件。达到预算只表示结束等待，不等于云同步成功。
- 检查选图取消、空间不足、本机文件丢失、页面退出、重进、进程重启与跨设备冲突。稳定性结论只覆盖实际完成的测试矩阵。

### 产品与数据

- 未记录不当作未服，本机待同步不当作云端已确认。
- 一盒一份库存与计划；“新购一盒”不继承旧盒历史、照片或计划。
- 表单预览、今天任务、后台计算复用已有日期与计划规则；生成代码只能通过构建脚本更新。
- 上传或反馈不得增加药名、图片、位置、剂量或原始账号标识的日志输出。
- 当前 UI 与包体基线需要在阶段 0 实测；新增组件导致明显增长时提供前后对比，不先全量引入第三方库。

## 9. 发布与回退

只影响展示的工作包可独立发布和回退；涉及字段或接口时服务端先兼容、客户端后启用。

位置字段保持可选，回退客户端不要求删除字段。队列新增字段需要旧记录读取兼容；若未来使用不兼容结构，另设存储版本并保留待恢复任务，不能清空用户队列作为迁移方案。

集中盘点已确认的快照与新建药盒均为用户业务数据，回退版本不能自动删除。共享计划与提醒规则发生变化时须单独检查历史任务、已生成通知和日历数据。

每个工作包交付：代码与差异说明、对应行为测试、已执行设备矩阵、性能数据、已知限制和回退方法。未完成的真机或 UI 验收保留为发布前待办。

## 10. 本轮建议先确认的产品样稿

先设计并评审三张低保真页面：

1. **保存结果与照片修复**：字段确认、照片待同步、丢图重选、结果未知四种状态。
2. **计划表单中的未来 7 天预览**：有效输入、输入不完整、近期无安排、有效期截断四种状态。
3. **药箱与又买一盒**：位置标签、同药多盒、不同成员/规格不合并、新盒必填信息。

完成样稿与状态定义后，按第一轮顺序实施；第二轮的字段与会话设计再随实际反馈细化。
